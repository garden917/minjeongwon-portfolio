복잡한 운영 문제를 제품과 시스템으로 바꾸는 PM

흩어진 요구, 데이터, 정책, 외주, 보안 제약을 하나의 실행 가능한 문제로 다시 정의하고 실제로 굴러가는 운영 시스템을 남깁니다.

ERP, CRM, CMS, 모바일 앱, AI 챗봇, 재무 데이터 개선을 “한 일 목록”이 아니라 반복 가능한 PM 운영체계로 보여주는 포트폴리오입니다.

핵심 질문

“이 문제는 정말 기능 문제인가, 아니면 운영 구조·데이터 흐름·의사결정 방식의 문제인가?”

저를 설명하는 5가지 방식

최종본은 프로젝트 수보다 반복되는 일의 방식을 앞에 둡니다. 정원님의 강점은 결과물 이름보다 문제를 다루는 방식에 있습니다.

문제를 바로 요구사항으로 바꾸지 않음

표면 증상과 구조 원인을 나눈 뒤, 무엇을 만들지보다 왜 이 문제가 중요한지부터 정의합니다.

기술 제약을 제품 판단으로 번역

구현 책임자가 아니라 기술 제약과 사업 요구 사이의 선택지를 일정·리스크·사용자 영향 기준으로 좁힙니다.

실행 전 운영될 구조를 만듦

RFP, SRS, 외주 협업, 장애 대응, 유지보수 범위를 먼저 세워 오픈 이후에도 굴러가는 구조를 남깁니다.

데이터를 반박 도구로 사용

성과 장식보다 기존 가설을 버릴 수 있게 하는 검증 기준으로 숫자를 사용합니다.

AI를 일하는 방식의 변화로 봄

챗봇 기능이 아니라 학습, 권한, 오류 수정, 품질 게이트까지 포함한 AI 운영 프로세스를 설계합니다.

Execution

System Thinking

대표 사례

각 사례는 “무슨 일을 했다”가 아니라 PO/PM으로 어떤 판단을 했는지 중심으로 구성했습니다.

Case 01

CRM v2: 사용률 하락을 비즈니스 인프라 문제로 재정의

PO / PM
2023 - 현재
CRM은 화면이 아니라 영업과 데이터 운영의 인프라였습니다.

판단

사용률 95%->64.5% 하락을 단순 UX 불편이 아니라 고객 정보 유출, 상담 퍼널 분석 마비, DB 활용 로드맵 붕괴로 이어지는 문제로 해석했습니다.

실행

  • 실제 컬럼과 데이터 1만 건 요청, CX 상담 내역 직접 분류
  • CRM_WEB 백로그 27건을 SP1~SP6 사용자 흐름으로 재정렬
  • 상담신청 -> 버퍼계정 -> 설계사배정 -> 고객컨택 -> ERP계약 5단계 퍼널 정의
  • 19개월·상담 180만 건·계약 17만 건 분석

결과

CRM v2는 30명+ TF와 함께 3개월 안에 릴리즈되었고, 상담 물량보다 리드 품질과 시스템 커버리지가 중요하다는 논의 전환을 만들었습니다.

문제정의VOC퍼널 분석우선순위
Case 02

ERP 0->1: 없는 구조를 만들고 오픈 이후 운영 체계까지 남김

TPM / PM
2022 - 현재
기능 목록보다 더 오래 남은 것은 외주와 내부 조직이 같은 기준으로 일하는 방식이었습니다.

판단

보안 취약 레거시 교체를 단순 시스템 교체가 아니라 사용자 3,500명·계약 60만 건 규모의 전사 운영 구조 재설계로 봤습니다.

실행

  • 1차 범위를 MYGA 대체와 기존 운영 유지로 절단
  • 60명 TF를 개발·보안·DBA·DevOps·QA·운영·외주 기준으로 조율
  • RFP, SRS, 주간보고, 데이터 마이그레이션 기준, 외주 협업 프로토콜 정리
  • 유지보수와 별도 프로젝트를 분리하는 외주 운영 구조로 재설계

결과

ERP는 CRM, CMS, SAP, 설계사 앱의 기준 시스템이 되었고, 이후 외주 협업에도 재사용 가능한 운영 체계가 남았습니다.

0->1시스템 운영외주 협업범위관리
Case 03

CMS/재무 데이터: 정산과 회계를 시스템 무결성 문제로 끌어올림

PM
2022 - 현재
월말 정산 업무를 내부 통제와 회계 무결성을 지탱하는 시스템 문제로 재정의했습니다.

판단

수수료 정산 오류는 사람의 검산 문제가 아니라 ERP-CMS-SAP 데이터 흐름, 검증 로직, 회계 기준의 연결 문제였습니다.

실행

  • 월 100억+ 정산 로직 표준화와 수수료율 검증 로직 3개 설계
  • 채권관리규정 댓글 125개를 구현 5개 + 변경 4개 명세로 수렴
  • 태아 등재 6,825건 누락과 IFRS 3.9억 리스크 수치화
  • 갱신형 회차역전 +12 고정 보정안을 SQL로 반박, 동적 보정 제시

결과

정산 자동화와 재무 데이터 이상 탐지가 단발 수정이 아니라 DB·로직·UI 재발 방지 구조로 이어졌습니다.

회계 무결성데이터 검증리스크 수치화재발 방지
Case 04

AI 도입: 챗봇 기능이 아니라 AI 운영 프로세스를 만든 사례

PM
2024 - 현재
AI를 붙이는 것보다 중요한 것은 학습, 권한, 오류 수정, 품질 게이트가 운영되는 방식이었습니다.

판단

AI 챗봇 도입을 기능 실험이 아니라 반복 문의와 문서 탐색 비용을 줄이는 운영 프로세스 개선으로 봤습니다.

실행

  • 인켑의 학습 방식, 정보 유출 리스크, 비용 구조 검토
  • 벤더와 직접 소통해 슬랙 자동 학습 인제스터 세팅
  • 인슈헬프봇 답변 범위 재분류와 데이터셋 오류 수정
  • AI 코드리뷰 + 이의 제기 프로세스로 품질 게이트 설계

결과

사내 첫 AI 챗봇은 PoC에서 운영 단계로 안착했고, 웹 확장과 전사 AI 협업 프로세스로 이어졌습니다.

AI 운영품질 게이트프로세스 설계ROI 관점
Case 05

보안 협업 R&R: 갈등을 사람 문제가 아니라 흐름 문제로 재설계

PM / Product Ops
2026
“보안팀이 막는다”가 아니라 정보 비대칭과 판단 순서의 문제였습니다.

판단

정책으로 먼저 차단하는 구조를 기술 검증 -> 정책 검토 -> 현업 리스크 수용 순서로 바꾸는 협업 구조를 제안했습니다.

실행

  • 정보 비대칭과 판단 순서 문제로 갈등 원인 분해
  • 보안평가팀, 인슈어런스보안팀, 현업 3자 R&R 재설계
  • 각 이해관계자에게 이익이 되는 구조로 제안

결과

“무조건 안 된다”는 대립을 실제 리스크 수준을 먼저 파악하고 되는 방향을 찾는 구조로 전환했습니다.

R&R리스크 우선갈등 구조화조직 설계

작은 사례로 보이는 반복 패턴

Product Discovery

고객·현업 데이터 직접 분류

CSAT -> NPS 시퀀스, CX 상담 직접 분류, CRM 사용 데이터 1만 건 요청으로 무엇을 만들지의 근거를 만들었습니다.

Operations

5~7개 병렬 과제 가시화

주간 성과 브리핑을 정례화해 핵심 요약, 성과 내용, 다음 주 업무를 전사에 공유했습니다.

Strategy

팀 정체성 언어화

Product Platform Team을 시스템 담당팀이 아니라 전략적 페이스메이커이자 조율자로 정의했습니다.

제가 잘 맞는 역할

B2B/B2B2C 운영 제품 PO

여러 사용자군, 권한, 정책, 데이터 정합성, 운영 프로세스가 얽힌 제품에 강합니다.

시스템/플랫폼 TPM

여러 시스템과 외주사가 연결되는 환경에서 목적, 범위, 우선순위, 리스크를 정리합니다.

AI Workflow PM

AI 기능보다 학습 데이터, 권한, 실패 모드, 성과 지표, 품질 게이트를 설계합니다.

Product Operations

정산, 회계, 외주, 보안, 장애, 데이터 품질 문제를 제품 과제로 끌어올립니다.

요약

제가 잘할 수 있는 일은 복잡한 시스템 제품에서 “무엇을 만들지”보다 먼저 “왜 이 문제가 중요하고, 어떤 구조로 풀어야 오래 가는지”를 정의하는 일입니다.
